# 意外停机与自动处理链恢复机制

## 背景

DanmakuRender 的直播处理链包含录制、渲染、上传和清理等异步阶段。原有实现只在渲染或上传明确失败，以及程序正常调用 `stop()` 时保存失败任务。断电、进程崩溃或强制结束可能导致：

- 正在渲染或上传的任务只存在于内存中，重启后无法找回。
- `LiveEvents.state_dict` 丢失，单独重试渲染后无法继续自动上传和清理。
- 阶段切换消息已经生成但尚未进入下一个插件队列时丢失。
- 任务已经完成，但完成消息尚未被编排层消费时重复执行。
- 延迟清理任务在重启后丢失。

恢复机制的目标是让未完成的自动处理链在程序重启后可被识别，并从 Web 界面恢复渲染或上传，随后继续执行下游阶段。

## 恢复语义

该机制提供“至少一次”恢复，不承诺跨本地程序和远程上传平台的严格一次执行。

- 中断的渲染任务由用户在 Web 页面确认后从头重新渲染。
- 中断的上传任务由用户确认后重新上传。
- 已经成功、但成功消息尚未被编排层确认的渲染或上传任务，只重新投递成功结果，不重复执行任务。
- 已被 Cleaner 接收的清理任务在重启后自动恢复。
- 阶段切换消息通过持久化 outbox 重放，并使用 `request_id` 去重。

远程平台可能已经接收上传，但程序在保存成功状态前停止。此时无法仅依靠本地状态判断远程结果，重新上传仍可能产生重复投稿。

## 状态文件

恢复状态保存在 `.temp/` 中，该目录属于运行状态，不应提交到 Git。

## 禁用恢复

默认会恢复所有录制任务。若不希望恢复任何录制任务，可在 `global.yml` 的
`dmr_engine_args` 中设置：

```yaml
recover_pipeline: false
```

也可仅对不需要恢复的任务，在对应 `DMR-*.yml` 的 `common_event_args` 中设置：

```yaml
recover_pipeline: false
```

单任务设置优先于全局设置。关闭后，启动时会删除该任务旧的流水线状态和待投递消息，
但不会删除任何已录制、渲染或下载的视频文件；渲染、上传、清理插件各自的失败任务列表
不受这个开关影响，仍可在 Web 页面按需处理。

| 文件 | 内容 |
| --- | --- |
| `.temp/active_renders.json` | 已接收但尚未被流水线确认完成的渲染任务 |
| `.temp/failed_renders.json` | 渲染失败、意外中断或等待恢复确认的任务 |
| `.temp/active_uploads.json` | 已接收但尚未被流水线确认完成的上传任务 |
| `.temp/failed_uploads.json` | 上传失败、意外中断或等待恢复确认的任务 |
| `.temp/active_cleans.json` | 等待执行、执行中或失败的清理任务 |
| `.temp/replay_states/<hash>.json` | 各 ReplayTask 的 `LiveEvents` 流水线状态 |
| `.temp/replay_outbox/<hash>.json` | 尚未收到目标插件接收确认的阶段切换消息 |

`<hash>` 是任务名的 SHA-256，用于避免任务名中的特殊字符影响文件路径。状态文件使用“同目录临时文件 + `os.replace`”方式原子替换，降低进程停止时写出截断 JSON 的概率。

任务状态主要包括：

- `waiting`：已进入插件队列，等待执行。
- `rendering`、`uploading`、`cleaning`：对应阶段正在执行。
- `failed`：任务执行失败。
- `interrupted`：上次程序停止时任务尚未完成。
- `completion_pending`：任务已经成功，但成功结果尚未被 ReplayTask 确认。

## 恢复流程

### 任务进入插件

1. ReplayTask 在发送 `newtask` 前将消息写入自己的 outbox。
2. Render、Uploader 或 Cleaner 收到消息后，先按 `request_id` 检查是否已存在。
3. 插件将任务写入活动任务文件。
4. 插件向 ReplayTask 返回 `accepted`。
5. ReplayTask 收到确认后删除对应 outbox 消息。

如果程序在任一步骤停止，重启后 outbox 会重新发送消息；插件通过 `request_id` 去重，因此不会重复创建同一任务。

### 渲染完成

1. Render 将任务状态改为 `completion_pending`，保存输出 `VideoInfo`。
2. Render 向 ReplayTask 发送 `render/end`。
3. `LiveEvents.onRenderEnd` 更新持久化流水线状态，并生成需要的上传任务。
4. ReplayTask 返回 `ack`。
5. Render 收到确认后从活动任务文件删除该任务。

如果第 2 至第 4 步之间停止，任务会在 Web 页面显示为等待确认。点击恢复后仅重新投递 `render/end`，不会再次渲染。

### 上传完成

上传使用相同的 `completion_pending` 和 `ack` 流程。ReplayTask 处理 `uploader/end` 后更新流水线状态，并按配置生成清理任务。

如果上传已经返回失败，包括原实时上传任务失败，任务会保存到失败列表。实时上传使用的内存队列不可恢复，重试时会基于已录制的本地文件转为普通上传。

### 清理恢复

Cleaner 在接受任务时保存任务及计划执行时间。重启后：

- 尚未到执行时间的任务继续等待剩余时间。
- 已到执行时间或执行中断的任务重新进入单线程清理执行器。
- 文件已经不存在时沿用现有行为，记录警告并跳过。

复制、移动、自定义命令等动作是否可安全重复，仍由具体清理配置和外部命令保证。

## Web 操作

启用 `webservice` 插件后，可在 `/tasks` 页面查看：

- 当前渲染和上传队列。
- 失败或意外中断的渲染任务。
- 失败或意外中断的上传任务。
- 任务状态及失败原因。

点击“重试”前会检查输入文件：

- 渲染任务要求原视频仍然存在。
- 上传任务要求全部待上传文件仍然存在。

检查失败时任务会保留在失败列表，并在页面提示缺失文件。

上传任务重试可能产生重复投稿，应先检查远程平台状态。删除失败任务只删除恢复记录，不删除本地视频。

## 序列化约定

状态恢复会重新构造：

- `VideoInfo`
- 嵌套的 `StreamerInfo`
- `ctime` 和 `stream_start_time` 时间字段

`stream_queue` 属于仅在进程内有效的运行时对象，写入状态文件时统一替换为 `null`。新增任务字段时必须确认其可被 JSON 序列化；不能序列化的句柄、线程、锁、队列和进程对象不得写入持久化任务。

上传任务状态中仍包含执行上传所需的配置参数，因此 `.temp/` 可能包含账号配置或其他敏感信息。该目录必须保持在 `.gitignore` 中，不应对外共享。后续如调整上传配置结构，需要同时验证旧状态文件的兼容性。

## 测试

基础验证：

```powershell
python -m unittest DMR.tests.test_recovery -v
python -m compileall -q DMR
python main.py --version --skip_update
```

恢复测试覆盖：

- 嵌套时间字段反序列化。
- 活动渲染任务在重启后转为中断任务。
- `completion_pending` 渲染结果直接重新投递。
- `LiveEvents` 恢复后，渲染完成继续生成上传任务。
- outbox 在重启后保留消息，直到收到插件接收确认。

涉及真实录制、上传和删除的测试不能作为普通单元测试运行。手动测试时应使用独立测试账号、短视频和无破坏性的清理配置。

## 维护注意事项

- 新增自动处理阶段时，应同时实现活动任务持久化、接收确认、`request_id` 去重和完成确认。
- 修改 `LiveEvents` 状态结构时，需要考虑旧 JSON 状态文件的兼容或迁移。
- 不要在任务成功后立即删除活动记录；必须等待 ReplayTask 的 `ack`。
- 不要先删除 outbox 再持久化目标任务。
- 保持状态写入为原子替换，避免直接覆盖 JSON 文件。
- 删除或重命名任务配置后，对应哈希状态文件不会自动迁移到新任务名。
- 平台断点续传、远程稿件查询和严格幂等不属于当前机制，不能把本地恢复状态视为远程平台最终状态。
